# related note における「特徴的内容」抽出の設計案

## 背景

- 現状は `notes.embedding`（ノート全文の単一ベクトル）で近傍検索しているため、ノート全体のトーンが似た候補が上がりやすい。
- 既存実装では `notes/{noteId}/sections/*` にセクション埋め込みが生成済みだが、`searchRelated` では未活用。
- 目標は「ノート内の特徴的な内容」に寄せた関連ノート提案。

## 前提と制約

- 大規模コーパスはない。
- Firebase中心で構成する（Firestore + Functions + 既存Vertex/Gemini利用）。
- Firestore vector search の次元上限は 2048（現状は 3072 -> 2048 に射影済み）。

## 評価軸

- 精度: 本当に関連するアイデアが出るか
- 多様性: 似すぎる候補だけにならないか
- 実装難易度: 既存コードにどれだけ自然に入るか
- 運用コスト: 再計算、APIコスト、失敗時の扱い

## 案1: セクション単位ベクトル検索 + ノート集約（最有力）

### アイデア

- ノート全体ではなく、編集中ノート内の「セクション（または段落）」をクエリにして `sections` で近傍検索。
- ヒットした section を `noteId` 単位で集約して related note を返す。

### 実装イメージ

1. `searchRelated` で `queryText` がある場合:
   - そのテキストを埋め込み化して `collectionGroup("sections")` に `findNearest("embedding", ...)`。
2. `queryText` がない場合:
   - 対象ノートの sections を数件読み、代表セクション（後述の特徴スコア上位）をクエリに使う。
3. 集約:
   - `noteId` ごとに `max(similarity)` + `top-k section hit count` でスコア化。
4. 返却:
   - 上位ノートを `notes` から読み直して返す。

### メリット

- 既存データ（`sections.embedding`）を活用できる。
- 「ノート内のどの観点が似ているか」が取りやすい。
- 全体要約っぽい埋め込みに引っ張られにくい。

### デメリット

- クエリ回数が増え、レイテンシがやや上がる。
- セクション分割品質に依存する（見出しがないノートは弱い）。

### 変更箇所

- `functions/src/search.ts`: notes検索から sections検索 + note集約へ。
- 必要に応じて `functions/src/triggers.ts`: 見出しなし文書向けの段落分割補強。

## 案2: TF-IDFで特徴キーワード抽出 -> キーワード埋め込み検索

### アイデア

- ノート内の語を TF-IDF で重み付けし、上位キーワード（または keyphrase）だけを埋め込んで検索する。

### 実装イメージ

1. ノート更新時にトークン化（日本語は簡易形態素 or n-gram）。
2. `df(term)` をユーザー単位で Firestore に保持（`users/{uid}/termStats/*`）。
3. `idf = log((N+1)/(df+1)) + 1`、`tf-idf` 上位を抽出。
4. 上位M語を1本ずつ埋め込み、候補検索後にスコア統合。

### メリット

- 「特徴語」を明示的に使えるので説明可能性が高い。
- 大規模コーパス不要（ユーザー内コーパスで成立）。

### デメリット

- 日本語トークン化の品質次第で精度がブレる。
- 語彙が短い・曖昧な語は埋め込み検索でノイズ化しやすい。
- `df` 更新処理が増え、運用がやや重い。

### Firebase実装上の注意

- Firestore更新回数を抑えるため、`df` はバッチ更新 or 定期再計算を推奨。
- 初期データが少ない期間は IDF が不安定なので、stopword辞書を併用する。

## 案3: Geminiで「重要キーワード/主張」を抽出 -> 埋め込み検索

### アイデア

- LLMに「このノートで固有性の高いキーワード・主張・名詞句を抽出させる」。
- 抽出結果（例: 5〜10件）を埋め込み検索に使う。

### 実装イメージ

1. `onNoteWritten` で GeminiにJSON出力を要求:
   - `keywords[]`, `key_claims[]`, `confidence`
2. `notes` に `salientKeywords`, `salientClaims` を保存。
3. `searchRelated` でそれらをクエリ化し、候補を統合ランキング。

### メリット

- ルールベースより文脈理解が強い。
- 複合語・言い換え・専門語に強い。

### デメリット

- コスト/レイテンシ増。
- 出力揺れ対策（JSON schema検証、再試行）が必要。
- 抽出品質を安定させるプロンプト設計が必要。

### 備考

- 既に Vertex/Gemini を使っているため、アーキテクチャ整合性は高い。

## 案4: キーセンテンス抽出（TextRank/埋め込み中心性）-> 文埋め込み検索

### アイデア

- ノートから「代表文」ではなく「特徴文」を数文抽出して検索。
- 例: 文同士の類似グラフを作り、中心性が高すぎる一般文を避ける重み付けを入れる。

### 実装イメージ

1. 文分割（`。` / 改行ベース）。
2. 文埋め込みを作成。
3. スコア:
   - `salience = novelty * local_importance`
   - novelty は「ノート平均との差分が大きい文」を優先。
4. 上位K文をクエリに検索し、ノート単位で集約。

### メリット

- キーワードだけより文脈を維持しやすい。
- 「その文脈に本当に近いノート」を拾いやすい。

### デメリット

- 埋め込み回数が増え、コスト高。
- 実装がやや複雑（文分割・重複排除・集約）。

## 案5: ハイブリッド検索（Sparse + Dense）

### アイデア

- Dense検索（埋め込み）に、軽量なSparseスコア（BM25/TF-IDF一致）を足し合わせる。
- 例: `final = 0.7 * dense + 0.3 * sparse`。

### 実装イメージ

1. ノートごとに `topTerms` を保存。
2. `searchRelated` で dense候補上位Nを取得。
3. その候補にだけ sparse再ランキングをかける（全件走査しない）。

### メリット

- Dense単独の「意味は近いが焦点が違う」を抑制しやすい。
- 候補集合に対する再ランキングなので計算量を抑えやすい。

### デメリット

- スコア正規化が必要（dense/sparseのスケール差）。
- チューニング項目が増える。

---

## 案6: 多視点クエリ生成（Facet化）-> OR検索集約

### アイデア

- 1ノートを複数の「視点」に分解して検索する。
- 視点例: 問題定義 / 解決策 / 技術要素 / 制約 / 評価軸。

### 実装イメージ

1. ノート保存時に facet を抽出（ルール or Gemini）。
2. facetごとに埋め込みを作成。
3. 検索時は facetごとに近傍検索し、重複除去して集約。

### メリット

- ノートの一部観点にだけ強く関連する候補を拾える。
- 多様性が上がる（同質な候補に偏りにくい）。

### デメリット

- 実装・運用ともにやや重い。
- facet抽出品質が低いと逆効果。

## 比較まとめ（短評）

| 案                     | 精度   | 多様性 | 実装難易度 | コスト | 備考               |
| ---------------------- | ------ | ------ | ---------- | ------ | ------------------ |
| 1. セクション検索+集約 | 高     | 中     | 低〜中     | 低〜中 | 既存資産活用で最短 |
| 2. TF-IDFキーワード    | 中     | 中     | 中         | 低     | 説明しやすい       |
| 3. Gemini抽出          | 高     | 中〜高 | 中         | 中〜高 | 文脈理解が強い     |
| 4. キーセンテンス      | 高     | 中     | 中〜高     | 高     | 文脈保持に強い     |
| 5. Hybrid再ランキング  | 中〜高 | 中     | 中         | 中     | 安定化向き         |
| 6. Facet多視点         | 高     | 高     | 高         | 中〜高 | 最終形に近い       |

## 推奨導入順（現実的）

1. まず案1（セクション検索+集約）を導入

- 既存の `sections.embedding` が使えるため最短で効果が出る。

2. 次に案5（Hybrid再ランキング）を追加

- 取りこぼしを減らしつつ、精度のブレを抑える。

3. 高精度化フェーズで案2 or 案3を追加

- 運用コスト優先なら案2、精度優先なら案3。

## 計測指標（最低限）

- Suggestクリック率（CTR）
- SuggestからのMix採用率
- 同一ノート再提示率（多様性の逆指標）
- ユーザー手動除外率（ノイズ指標）

## 実装時の補足

- `searchRelated` は結果に `matchedBy`（`section` / `keyword` / `claim`）を含めるとデバッグしやすい。
- ノート更新直後に埋め込み未生成の期間があるため、現行同様にフォールバック（最近更新ノート）を残す。
- 2048次元制約は現行のランダム射影方針を維持する。
